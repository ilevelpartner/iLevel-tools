§1Logo crush — bug, ship immediately

The logo renders at 18 × 5px at a 1033px viewport. Source image is 2560 × 677. Under 15 minutes to fix.

Cause .site-header .header-top is display:flex with four children. Three cannot shrink, so .header-logo absorbs 100% of the overflow — and its img carries max-width:100%, so it scales down without limit.

Affected band ≈ 1025–1190px. Includes any non-maximized window, and 1366×768 laptops at 125% Windows scaling (≈1093 CSS px) — common in independent retail back offices.

Fix

/* the only change needed */
.site-header .header-top .header-logo { flex: 0 0 150px; }

The existing @media (max-width:1199px) rule setting width:150px is correct and stays — it just needs flex-shrink:0 alongside it.

  • No horizontal scrollbar between 1024 and 1440

§4Directional retracting header

Buyer laptops commonly render ~625 CSS px of viewport height. A static two-band header consumes ~17% of that permanently.

Scroll stateWrapper inline style
At toptop: 0px
Scrolling downtop: -{measuredHeaderHeight}px
Scrolling uptop: 0px
  • A wrapper div is position:sticky with transition on top, 200ms ease-out. The header itself stays position:relative inside it.
  • Sticky rather than fixed keeps it in normal flow — no layout jump, no scroll-position correction.
  • Header height is measured once and exposed as a CSS variable. Every downstream sticky offset reads it (§12). Do not hardcode.
  • Never retract within ~160px of the top. Hold open while a dropdown is expanded or a control inside has focus. Respect prefers-reduced-motion.
Note position:sticky fails silently inside an ancestor with overflow: hidden|auto|scroll. Check the ancestor chain before debugging anything else.

Acceptance

  • Logo, nav and pills all visible on one line at 1030, 1100, 1150, 1190, 1440
  • Account block collapses to avatar below ~1100px without the nav wrapping
  • Header retracts on scroll-down, returns on scroll-up, no content jump
  • Nav identical on shop, PDP, cart, checkout and post-registration

§5DC pills

Band 2. Every source the buyer holds, plus an Add DC pill. Replaces the Manage DCs dropdown.

Why pills, not a dropdown The dropdown made active state invisible — a buyer could not tell at a glance which DCs were live without opening a menu. Pills make state readable without interaction. Any implementation that hides state behind a control has missed the point.

Toggle behaviour

StateAppearanceTap
OnCream fill, orange distributor, green dotToggles off
OffGrey fill, hollow dot, muted textToggles on
  • No floor. All pills may be toggled off. Result is an empty grid with a recovery message (§13) — a legitimate state, not an error.
  • Toggling is a view filter on the catalog query only. It must not re-route, remove or alter cart lines. A buyer with cart lines at a DC they toggle off keeps those lines untouched.
  • Toggle state is per-session and non-durable. On every new login all held pills are lit, regardless of how the buyer left them. Reset on session start, not page load — resetting per page load would make the toggle useless.

Add DC pill

A dashed pill at the end of the distributor pills, opening the Add DC panel (§7). It is the only non-lit element in the row, so grey is never ambiguous. It is also the repeat mechanism: adding two DCs means tapping it twice — which is why the panel handles one DC at a time.

§6First Mile

A Palko drop-ship program — ordered by the case, freight on the brand, not DC-scoped. Only some brands are enrolled.

Palko appears in the distributor select like any other. Its DC select has two options: Warehouse and First Mile. A buyer with a Palko account may add either or both using the same account number — no separate approval. Two rows means two pills, which is correct: they are separate fulfillment paths generating separate POs.

§7Add DC panel

The existing dc-popup-box with dc-repeater-row and dc-add-btn is replaced, not patched. It is built as a list manager, which is why it reads as confusing — the buyer opens it to do one thing and is shown an interface implying several.

One component, two contexts The Add DC panel and registration Step 3 (§8) are the same component. Not similar — identical, so they cannot drift when one is edited. At registration it carries first-run copy; from the pill it does not.

Rules

  • One DC per submission. No repeater rows, no add-another-row control.
  • Account confirmation is plain double-entry — do the two strings match, exactly as the password fields work. No external validation in this release.
  • Match on exact string after trimming whitespace only. Do not normalise case or strip characters — KeHE and UNFI account numbers carry real suffixes, and transforming them creates a mismatch between what the buyer sees and what appears on the PO.
  • Store the number exactly as entered.
  • Both number fields get a show/hide eyeball, same control as the password fields. Buyers are copying a string off an invoice into two fields that must match — they should be able to check it against the paper.
  • Cancel, not help. Opening a distributor account is between the buyer and the distributor, not a Turnpike flow.
  • DC select is disabled until a distributor is chosen, reading Select distributor first.
  • Add is disabled until valid.
  • On success: panel closes, the new pill appears lit with a brief highlight.
  • First DC added is flagged primary automatically. A "make primary" control appears on rows only once a buyer holds more than one. If a primary DC is removed, the flag moves to another row.

§8Registration

Buyers are granted access on registration. There is no approval queue — accounts may be revoked afterwards if needed.

Live and wrong The thank-you page reads "Turnpike opens for business before the end of the month and because you registered early, you'll be one of the first we notify when it goes live." That is leftover pre-launch messaging — the same account is simultaneously logged in and browsing the catalog. Replace with confirmation plus entry.

Step 3 — First DC

Stays its own page. Steps 1 and 2 collect facts about the buyer; Step 3 creates their first source. Uses the Add DC component (§7) with first-run copy:

  • Heading: Add your first DC
  • Sub: Just one to open your account — you can add more anytime.
  • On success: Added. Add another now, or do it later from Add DC in your header.

That last line names the exact control the buyer will look for, which is what makes the Add DC pill legible when they reach the catalog.

Terms once only Terms and Privacy are agreed at Step 3, at account creation. The checkbox is removed from the review/checkout screen — a buyer who agreed at signup should not re-consent on every order. This also removes a stock WooCommerce leak.

Other

  • Normalise email to lowercase on save. A capitalised TLD was observed (david@texasilb.Com). It will deliver, but any exact-match lookup downstream — Klaviyo dedupe, crosswalk, routing — will split the record.
  • Store Size renders as a raw browser select while Step 3 uses the styled control. Unify on the styled control.
  • The number-of-locations dropdown overlaps and hides the Street address field beneath it.
  • Confirm whether reCAPTCHA on Step 3 is wanted given the goal is a fast signup. Flagging, not prescribing.

§10Product detail page

The gap below the image

The gallery/summary row stretches both columns to equal height. The summary column runs out of content first, leaving a large empty region that pushes everything below it down. Categories and Brand are pinned to the bottom of that stretched row.

Do not Do not fix this with negative margin, a fixed height, or a top-margin adjustment on the tab box. Those treat the symptom.
  • Change the gallery/summary row to size to content rather than stretch (align-items: flex-start rather than stretch or an equal-height rule)
  • Move Categories and Brand out of that row into a normal full-width block beneath it

Tabs

  • Remove the Additional Information tab — stock WooCommerce scaffolding
  • With one tab remaining, remove the tab strip. A single heading over the text is correct; a lone tab implies others exist
  • The description currently appears twice on the same page — once in the summary column beside the price, once in the Description tab. Keep the tab copy, remove it from the summary column. The summary description is what pushes the buy controls below the fold

Rules

  • Selector renders only where the product is available at 2 or more of the buyer's lit sources. Otherwise static text or nothing
  • Changing a line's DC re-groups immediately, not on Update Cart — otherwise the group header above contradicts the selection beneath it
  • The review step stays read-only. Changing routing on the final screen re-splits POs at the worst moment
  • Account number chip moves to the group header. Beside the Brand chip it reads as though it belongs to the brand
  • The Update Cart row is currently a full-width bordered box containing one right-aligned button and nothing else. With quantity and DC changes applying immediately it may not be needed at all

Add-to-cart DC resolution

One rule, in order:

  1. If the buyer already has cart lines at a DC where this product is available, use that DC — consolidate
  2. Otherwise use the buyer's primary DC
  3. The buyer may change it on the cart line
Why primary exists Solely as the tiebreaker in step 2. It is not a preference buyers manage — it makes an otherwise arbitrary routing decision predictable and correctable. A single-DC buyer never encounters it.

§15Testing

Do not verify the header by eye on a single screen The logo defect is invisible above 1190px and invisible below 1024px. It only appears in the band between.
  • Test explicitly at 1030, 1100, 1150, 1190 and 1440 CSS px using device emulation
  • Confirm browser zoom is at 100% when measuring. Zoom multiplies with OS display scaling and will silently shift the viewport width being tested
  • Test pills with a buyer holding three or more DCs, including one Palko Warehouse and one Palko First Mile row on the same account number
  • Test the empty-catalog and all-pills-off states directly — they will occur in production
  • Test a mixed cart containing both a case-priced and a unit-priced line
